# قط الجشع — التشغيل والأمان

## الحالة الحالية

- اللعبة مستقلة كواجهة داخل موقع Happy Live الحالي: `/cat-greed/`.
- لوحة إدارة اللعبة: `/cat-greed-admin/`.
- مراقبة اللعبة وإدارة اللاعبين من لوحة Happy Live: قسم الألعاب.
- فتح اللعبة داخل الغرفة الصوتية من تبويب الألعاب المخصصة.
- لا يوجد مشروع Pages أو نطاق إضافي مطلوب.
- واجهات اللعبة ولوحاتها في Pages Preview لا تتصل بخادم الإنتاج؛ تبقى معطلة إلى أن يُجهّز Worker Preview معزول ويرتبط بعنوانه صراحة.
- اللعبة تبدأ **متوقفة**. لا تُفعّل قبل تطبيق migrations والتحقق من بيئة الاختبار.
- عند إيقاف اللعبة، تُمنع رهانات جديدة لكن تبقى الجولة الحالية مرئية حتى تنتهي وتُسوّى؛ لا تختفي رهانات اللاعبين أو نتيجتهم بسبب الإيقاف.

## ملفات اللعبة

- `backend/worker/src/cat_greed.ts`: API، الجولات، الرهانات، الصرف، الاحتمالات والصلاحيات.
- `backend/worker/migrations/0034_cat_greed_wheel.sql`: الجداول والإعدادات والرموز والجولات.
- `backend/worker/migrations/0035_cat_greed_ledger.sql`: دفتر حركات اللعبة.
- `backend/worker/migrations/0036_cat_greed_bet_protection.sql`: مفاتيح منع تكرار الرهان وحدود الطلبات والقيم الافتراضية الأكثر أماناً.
- `frontend/lib/pages/cat_greed_game.dart`: واجهة Flutter داخل الغرفة.
- `frontend/web/cat-greed/`: الموقع المستقل للعبة.
- `frontend/web/cat-greed-admin/`: لوحة اللعبة المستقلة.
- `frontend/web/admin/index.html`: لوحة الإدارة الرئيسية.
- `frontend/web/_headers`: سياسات أمان صفحات اللعبة.

## حدود الثقة والصلاحيات

1. اللاعب يحتاج جلسة Happy Live صالحة؛ لا يرسل العميل رصيداً أو نتيجة موثوقة.
2. الخادم وحده يخصم الرصيد ويحسب النتيجة ويضيف الجائزة.
3. لوحة اللعبة تقبل إعدادات الرموز والاحتمالات من المالك فقط.
4. لوحة Happy Live الرئيسية تسمح للمالك/المدير بمراقبة اللاعبين وتحديد سقف الرهان وإيقاف المشاركة؛ لا تغيّر احتمالات الفوز لكل لاعب.
5. لا تُكشف بذرة الجولة قبل إغلاق الرهان.
6. لا يستطيع أي لاعب اختيار النتيجة، ولا توجد نتيجة إدارية سرية أثناء استقبال الرهانات.

## سلامة الجولات والتحقق

تُحفظ إعدادات الرموز والمضاعفات والأوزان وإصدار قواعد اللعبة (`rulesVersion`) في `config_snapshot` عند إنشاء الجولة؛ لذلك لا تغيّر تعديلات الإدارة نتيجة جولة بدأت بالفعل.

- الالتزام المنشور قبل الرهان:
  `SHA-256("commit|" + seed + "|" + roundId + "|" + configSnapshot)`
- العينة التي تحدد النتيجة:
  `SHA-256("outcome|" + seed + "|" + roundId + "|" + configSnapshot)`
- بعد انتهاء الرهان يكشف الخادم البذرة والنتيجة والإعدادات المحفوظة.
- واجهة الويب تعيد حساب بصمة الالتزام محلياً، ثم تعيد حساب العينة والنتيجة من البذرة والإعدادات المحفوظة؛ وتعرض نجاح/فشل التحقق.
- لوحة اللعبة المستقلة تتيح للمالك تنفيذ التحقق نفسه من سجل الجولات بعد التسوية.
- بادئتا `commit|` و`outcome|` منفصلتان عمداً؛ نشر بصمة الالتزام لا يكشف العينة أو النتيجة قبل الإغلاق.

## الرصيد والرهانات

- الخصم يتم من `user_wallets` بشرط أن يكون الرصيد كافياً.
- كل خصم وجائزة يُسجل في `cat_greed_ledger` مع الرصيد بعد الحركة.
- لا يُستخدم `wallet_transactions` العام حتى لا تتغير قيوده أو وظائف المحفظة الحالية.
- كل رهان يتطلب UUID v4 كمفتاح `idempotencyKey`. إعادة الطلب بنفس المفتاح والبيانات لا تخصم مرة ثانية.
- مفتاح الرهان مربوط بالمستخدم والجولة والرمز والمبلغ؛ إعادة استخدامه ببيانات مختلفة تُرفض.
- الحد الافتراضي لمجموع رهانات اللاعب في الجولة مليون عملة، ويمكن للمالك/المدير تخفيضه.
- حماية الاندفاع: 10 طلبات رهان لكل لاعب خلال نافذة 10 ثوانٍ، و90 طلب تحديث حالة لكل لاعب خلال 60 ثانية؛ واجهة اللعبة تحدّث كل 1.5 ثانية لتبقى دون الحد.
- صرف الجوائز يستخدم مطالبة فريدة `paid_at + transaction_id` قبل تحديث المحفظة؛ الطلبات المتزامنة لا تصرف الجائزة نفسها مرتين.
- قيود D1 وفهارس إضافية تمنع تخزين نتيجة غير متوافقة مع حالة الجولة، وتفرض تفرد معرّف معاملة الجائزة، وتحسن استعلامات سجل اللاعب والإدارة.
- تحديث المحفظة ودفتر اللعبة ومعلومة الصرف داخل D1 batch واحدة.

## الاحتمالات والعائد النظري

تُحسب الاحتمالات من الأوزان العامة ونتائج السلطة/البيتزا، وتُعرض لكل اللاعبين وفي لوحة الإدارة:

- احتمال الظهور = احتمال الجولة المتبقي × وزن الرمز ÷ مجموع الأوزان.
- احتمال الفوز الفعلي يضيف احتمال النتيجة الخاصة التي تفوز بها فئة الرمز.
- العائد النظري = احتمال الفوز الفعلي × المضاعف. يُستخدم الحساب غير المدوّر ويُقرّب إلى الأعلى عند فحص حد التفعيل حتى لا يخفي التقريب زيادة في التعرض.
- يمنع الخادم تفعيل اللعبة إذا تجاوز العائد النظري لأي رمز 100% من قيمة الرهان.
- القيم الافتراضية الجديدة متوقفة، واحتمال السلطة 0.30% والبيتزا 0.30%، مع أوزان معدلة بحيث يبقى أعلى عائد نظري دون 100%.

| الرمز | احتمال الظهور | احتمال الفوز | العائد النظري |
|---|---:|---:|---:|
| 🐔 45x | 1.88% | 2.18% | 98.23% |
| 🍅 5x | 19.50% | 19.80% | 98.98% |
| 🐐 15x | 6.35% | 6.65% | 99.83% |
| 🌶️ 5x | 19.50% | 19.80% | 98.98% |
| 🐟 25x | 3.65% | 3.95% | 98.71% |
| 🥕 5x | 19.50% | 19.80% | 98.98% |
| 🦐 10x | 9.53% | 9.83% | 98.33% |
| 🌽 5x | 19.50% | 19.80% | 98.98% |

- هذه حماية من إعدادات خاسرة للمنصة، وليست ادعاءً بأن هامش المنصة 8%. لا تعتمد نسبة 92/8 قبل تثبيت معناها وقواعد دفع الجوائز؛ لا تُغيّر قواعد فوز السلطة/البيتزا سراً.

## حماية الواجهة والصور

- تقبل صور الرموز من نطاقات ImageKit عبر HTTPS فقط.
- يرفض الخادم روابط الصور ذات بيانات دخول أو منفذ غير قياسي أو نطاق خارج ImageKit.
- تُهرب القيم النصية عند إدراجها في HTML.
- ملفات JavaScript منفصلة عن HTML لتطبيق `script-src 'self'`.
- `frontend/web/_headers` يضبط CSP و`nosniff` و`Referrer-Policy` و`X-Frame-Options` و`Permissions-Policy` و`Cache-Control: no-store` على مساري اللعبة ولوحتها.

## API

- `GET /api/v1/games/cat-greed/state`: حالة الجولة، الرصيد، رهانات اللاعب، الاحتمالات وبصمة الجولة.
- `POST /api/v1/games/cat-greed/bet`: رهان موثّق مع `roundId`, `slot`, `amount`, `idempotencyKey`.
- `GET/PATCH /api/v1/admin/cat-greed/settings`: إعدادات الجولة والتشغيل؛ التعديل للمالك.
- `GET/PATCH /api/v1/admin/cat-greed/symbols`: الرموز والمضاعفات والأوزان والصور؛ التعديل للمالك.
- `GET /api/v1/admin/cat-greed/rounds`: سجل الجولات والبصمات والبذور المكشوفة بعد التسوية.
- `GET /api/v1/admin/games/cat-greed/overview`: لوحة المراقبة الرئيسية.
- `PATCH /api/v1/admin/games/cat-greed/players/:id`: إيقاف لاعب أو تعديل سقف رهانه.

كل مسارات الإدارة تتحقق من جلسة الإدارة وصلاحيتها على الخادم؛ إخفاء عناصر الواجهة ليس حماية.

## خطوات ما قبل الإطلاق

1. مراجعة PR وجميع التغييرات ومقارنة الملفات مع `main`.
2. تشغيل `npm test` و`npm run typecheck` من `backend/worker`.
3. تشغيل Flutter analyze/build للويب.
4. من `backend/worker` نفّذ `npm run db:preview:list` لمراجعة المعلّق، ثم `npm run db:preview` لتطبيق migrations على `happy-live-room-exp-preview-db` فقط. ملف `wrangler.preview-migrations.toml` مخصص لهذه القاعدة؛ لا تستخدم `db:remote` لأنه يستهدف D1 الإنتاج.
5. بعد نجاح migrations، أنشئ Worker Preview باسم `cat-greed` من مجلد `backend/worker` باستخدام `npm run preview:deploy` (Wrangler 4.135.0 أو أحدث). احتفظ بعنوان Preview الذي يرجعه الأمر.
6. اضبط أسرار ImageKit المطلوبة على Preview عبر `wrangler preview secret put`؛ لا تنسخ كلمات مرور أو أسرار الإنتاج ولا تحفظها في Git. أنشئ حسابات اختبار منفصلة داخل قاعدة Preview.
7. افتح صفحات Preview مع معامل `?catGreedApi=https://<preview-worker-host>` بعد التأكد من أن المضيف هو Worker Preview الخاص بـ Happy Live؛ الواجهة ترفض عنوان الإنتاج على صفحات Preview.
7. اختبار عدة لاعبين: الرصيد، طلبات مكررة، طلبات متزامنة، انتهاء الوقت، حدود الرهان، لاعب موقوف، صلاحيات الإدارة، وصرف الجائزة مرة واحدة.
8. التحقق من بصمة ونتيجة جولات فعلية في Preview، وتجربة صور ImageKit وCSP في المتصفح.
9. لا تطبق migrations على D1 الإنتاج ولا تنشر Worker/Pages ولا تفعّل اللعبة إلا بعد مراجعة نتائج الاختبار والموافقة على الإطلاق.

## التراجع

- اللعبة متوقفة افتراضياً؛ أوقفها من إعدادات اللعبة قبل أي تراجع.
- تراجع كود Worker لا يحذف جداول D1 ولا يعيد أرصدة اللاعبين تلقائياً.
- لا تحذف migrations أو جداول ledger/requests عند التراجع.
- عند وجود خلل مالي، أوقف اللعبة، احتفظ بسجلات `cat_greed_ledger` و`cat_greed_payouts`، وطابقها قبل أي تعديل يدوي على الأرصدة.
