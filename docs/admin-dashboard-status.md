# حالة لوحة إدارة Happy Live

آخر مراجعة: 2026-11-12

## البنية المعتمدة

- لوحة الإدارة مستقلة عن تطبيق Flutter: `frontend/web/admin/index.html`، وتُقدَّم من Cloudflare Pages على المسار `/admin/`.
- الخادم التشغيلي هو Cloudflare Worker في `backend/worker/src/index.ts`، وقاعدة البيانات هي D1 `happy-live-db`.
- Laravel في المستودع ليس API التشغيلية الحالية. ملف `backend/routes/api.php` يعرّف `GET /api/v1/health` فقط؛ لذلك لا تُخترع عقود إدارة Laravel ولا تُربط الواجهة به.
- المتصفح يتصل بـ Worker عبر HTTPS وBearer token فقط. لا توجد اتصالات D1 مباشرة من واجهة الإدارة.

## المصادقة والصلاحيات

- حسابات الإدارة والجلسات مستقلة عن حسابات المستخدمين في `admin_accounts` و`admin_account_roles` و`admin_sessions`.
- تسجيل الدخول: `POST /api/v1/admin/auth/login`. رمز الجلسة عشوائي، وتُخزّن تجزئته فقط في D1، وصلاحيته 12 ساعة.
- كلمات المرور تستخدم PBKDF2-SHA256 مع salt، بحد أدنى 100,000 دورة. تهيئة المالك لمرة واحدة تستخدم `ADMIN_SETUP_TOKEN`؛ لا يُخزّن الرمز أو كلمة المرور في المستودع.
- Worker يستخرج هوية المدير ودوره من جلسة D1 في كل طلب؛ لا يثق في role أو actor id يرسله المتصفح.
- الأدوار الحالية:
  - `owner`: كامل الصلاحيات.
  - `admin`: صلاحيات الإدارة التشغيلية المحددة في `ADMIN_ROLE_PERMISSIONS`، دون إدارة حسابات مديري اللوحة أو إضافة رصيد يدوي.
  - `moderator`: قراءة لوحة المعلومات والمستخدمين والغرف والتقارير وسجل التدقيق فقط.
- إدارة حسابات مديري اللوحة في هذا الفرع الجديد محصورة بالمالك، مع حماية حساب المالك ومنع تعطيله أو تغيير دوره.

## الوظائف المرتبطة بعقود Worker حقيقية على main

| القسم | نقاط API | الحالة |
|---|---|---|
| نظرة عامة وإحصائيات | `GET /api/v1/admin/overview` و`GET /api/v1/admin/stats` | إحصاءات حقيقية من D1 |
| المستخدمون | `GET /api/v1/admin/users` | بحث وقائمة حقيقية |
| تعليق/إعادة تفعيل الحساب | `PATCH /api/v1/admin/users/:id/status` | يغيّر حالة الحساب ويلغي جلساته عند التعليق |
| طرد المستخدم | `POST /api/v1/admin/users/:id/kick` | يلغي الجلسات الحالية فقط |
| مشرفو التطبيق | `GET /api/v1/admin/moderators` و`PATCH /api/v1/admin/users/:id/role` | إدارة الدور محصورة بالمالك |
| الغرف | `GET /api/v1/admin/rooms` و`PATCH /api/v1/admin/rooms/:id/status` | عرض وفتح وإغلاق |
| إشراف الغرفة | `GET/POST /api/v1/admin/rooms/:id/moderation` | مشرفو الغرفة، كتم، طرد 60 ثانية، حظر دائم ورفع الحظر |
| المحافظ | `GET /api/v1/admin/wallets` | رصيد المحفظة وسجل الحركات الفعلي |
| إضافة رصيد يدوية | `POST /api/v1/admin/users/:id/wallet/credit` | المالك فقط، وتُسجل كـ `admin_credit`؛ ليست بوابة شحن |
| الهدايا والإعدادات | `GET/PATCH /api/v1/admin/gifts/settings` | قراءة الإعدادات والإجماليات؛ تعديل نسب الأرباح للمالك فقط |
| كتالوج الهدايا | `GET/POST /api/v1/admin/gifts/catalog` و`PATCH/DELETE /api/v1/admin/gifts/catalog/:id` | إنشاء وتعديل وتعطيل هدايا فعلية؛ الحذف تعطيل منطقي |
| طلبات الهدايا المخصصة | `GET /api/v1/admin/gifts/custom-requests` و`PATCH /api/v1/admin/gifts/custom-requests/:id` | اعتماد الطلب وإنشاء هدية أو رفضه؛ المالك فقط |
| سجل الإجراءات | `GET /api/v1/admin/audit` | يعرض سجلات D1 وهوية المدير |

- الهدايا ليست صفحة وهمية: الإنتاج يحتوي فعليًا على `gift_catalog` و`gift_transactions` و`gift_custom_requests` وجداول دفتر الهدايا والمحفظة. كما توجد واجهات لإدارة الكتالوج وطلبات الهدايا المخصصة وتقسيم الإيرادات.
- إعداد السحب في D1 حاليًا `enabled = 0` و`agency_integration_ready = 0`. لا تُفعّل طلبات السحب ولا تُعرض كخدمة دفع مكتملة.
- عمليات الإدارة الحساسة على main تسجل هوية المدير في `details_json` داخل `admin_audit_logs`. هذا الفرع يضيف ربطًا علائقيًا، ويحوّل إدراجات الإجراءات الإدارية إلى مساعد واحد يكتب سجل الإجراء وربط المدير في دفعة D1 واحدة.

## ما لا توجد له عقود تشغيلية بعد

1. **VIP:** لا توجد جداول اشتراكات/عضويات VIP ولا نقاط API لمنحها أو تحديد تاريخ انتهائها؛ الصفحة تبقى غير مفعّلة.
2. **الشحن الإلكتروني:** لا توجد جداول طلبات شحن أو تكامل مزود دفع أو تحقق من Webhooks. إضافة الرصيد اليدوية للمالك ليست عملية شحن ولا يجوز عرضها كعملية دفع.
3. **السحب:** جداول الطلبات والإعدادات موجودة، لكن الإعدادات معطلة ولا توجد واجهات إدارة مكتملة للمراجعة والتسوية أو ربط الوكالات وKYC ومزود دفع.
4. **تفاصيل العقوبات:** حظر الغرفة دائم حاليًا والطرد المؤقت 60 ثانية؛ السبب يسجل في التدقيق، لكنه ليس حقلًا مستقلاً في سجل الحظر. لا توجد مدة حظر قابلة للانتهاء تلقائيًا.

## التغييرات الجديدة في فرع الأمان

الفرع: `security/admin-accounts-mainline-20261112`

- إضافة واجهات المالك:
  - `GET/POST /api/v1/admin/accounts`
  - `PATCH /api/v1/admin/accounts/:id/role`
  - `PATCH /api/v1/admin/accounts/:id/status`
  - `POST /api/v1/admin/accounts/:id/password`
  - `POST /api/v1/admin/accounts/:id/revoke-sessions`
- إنشاء مدير أو مشرف قراءة فقط، وتغيير دوره، وتعطيله أو تفعيله، وتدوير كلمة مروره، وإبطال جلساته. التعطيل وتدوير كلمة المرور يسحبان الجلسات السابقة.
- لا يمكن إنشاء مالك إضافي من الواجهة، وحساب `owner` محمي حتى لو غاب ربط دوره لأي سبب.
- صفحة عربية متجاوبة «مديرو اللوحة» تظهر للمالك فقط؛ مع ذلك، جميع الحماية الفعلية داخل Worker.
- تضييق CORS لقبول الأصول المحددة صراحةً في `ALLOWED_ORIGINS` فقط، بدل قبول أي نطاق فرعي ينتهي بـ `.happy-live.pages.dev`. يلزم إضافة أي نطاق معاينة موثوق صراحةً قبل استخدامه.
- migration جديدة: `0031_admin_audit_actor_refs.sql`؛ رقمها بعد migrations الحالية حتى `0030_custom_gift_media.sql`. تنشئ علاقة FK بين سجل التدقيق وحساب المدير، وتعيد ربط السجلات القديمة التي تحتوي `adminId` صالحًا في JSON.
- تم توحيد سجل التدقيق العلائقي لإجراءات المحافظ وAgora والمستخدمين والغرف والهدايا وإدارة حسابات المديرين. سجل تغيير نسب الأرباح يبقى أيضًا في `gift_revenue_settings_audit` مع `admin_id`.

## فحص الإنتاج للقراءة فقط — 2026-11-12

تم الاستعلام من D1 مباشرة عبر Cloudflare API بصلاحية قراءة فقط، ولم تُجرَ أي كتابة:
- حساب الإدارة `owner` موجود ونشط.
- جداول الإدارة الأساسية وجداول المحفظة والهدايا موجودة.
- توجد بيانات فعلية في كتالوج الهدايا ومعاملات إرسال الهدايا.
- إعدادات السحب ما زالت معطلة وغير جاهزة لتكامل الوكالات.
- لا توجد جداول تحمل أسماء VIP أو recharge أو payment.
- جدول `admin_audit_actor_refs` غير موجود في الإنتاج حتى الآن؛ لا يُنشر Worker الجديد قبل تطبيق migration `0031`.
