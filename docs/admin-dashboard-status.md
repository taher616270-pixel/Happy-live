# حالة لوحة إدارة Happy Live

آخر مراجعة: 2026-11-12

## البنية الفعلية

- لوحة الإدارة مستقلة عن Flutter: `frontend/web/admin/index.html` وتُقدَّم من Cloudflare Pages على المسار `/admin/`.
- واجهة المستخدمين الأساسية تبقى في تطبيق Flutter. لا ينبغي تحويل مسار `/admin/` إلى صفحة Flutter أو عرض واجهة المستخدمين فيه.
- الخادم التشغيلي هو Cloudflare Worker في `backend/worker/src/index.ts`، ومصدر البيانات هو D1 `happy-live-db`.
- Laravel في `backend/` هيكل تاريخي غير نشط. ملف `backend/routes/api.php` لا يحتوي عقود إدارة تشغيلية؛ `backend/README.md` يحدد Worker بوصفه الخلفية المعتمدة. لا تُخترع نقاط Laravel أو تُربط بها الواجهة.
- المتصفح يتصل بـ Worker عبر `fetch` مع رمز Bearer فقط؛ لا توجد D1 credentials أو استعلامات SQL في صفحة الإدارة.

## المصادقة والصلاحيات

- حسابات الإدارة منفصلة عن حسابات مستخدمي التطبيق في `admin_accounts` و`admin_account_roles` و`admin_sessions`.
- تسجيل الدخول: `POST /api/v1/admin/auth/login`. الخادم يخزن تجزئة رمز الجلسة، والجلسة صالحة 12 ساعة.
- كلمات المرور تُخزَّن باستخدام PBKDF2-SHA256 مع salt؛ لا تُحفظ كلمات المرور الصريحة.
- `GET /api/v1/admin/me` يستخرج الدور من D1 عبر جلسة الإدارة. لا يثق Worker في `role` أو `adminId` يرسلهما المتصفح.
- التهيئة الأولى تستخدم `GET /api/v1/admin/auth/setup-status` و`POST /api/v1/admin/auth/setup` وتتطلب سر Worker `ADMIN_SETUP_TOKEN` لمرة واحدة وكلمة مرور لا تقل عن 12 حرفًا.
- حساب المالك في الإنتاج مهيأ بالفعل. لا توجد كلمة مرور في المستودع ولا تُخترع بيانات دخول.
- الصلاحيات الحالية:
  - `owner`: جميع الصلاحيات، وإدارة حسابات مديري اللوحة.
  - `admin`: إدارة المستخدمين والغرف، الإشراف، التقارير، الإعدادات المسموح بها، وقراءة بيانات الهدايا والمحافظ.
  - `moderator`: قراءة محدودة فقط؛ لا تظهر له صفحات إدارة المالك أو العمليات المالية.
- تعطيل مدير أو تدوير كلمة مروره يبطل جلساته. حساب المالك محمي من التعديل عبر واجهات إدارة الحسابات.

## الوظائف المربوطة بعقود حقيقية

| القسم | نقاط API | الصلاحيات / الحالة |
|---|---|---|
| الرئيسية | `GET /api/v1/admin/overview` | أعداد فعلية من D1 |
| الإحصائيات | `GET /api/v1/admin/stats` | المستخدمون والغرف والمنشورات والرسائل |
| المستخدمون | `GET /api/v1/admin/users` | بحث وقائمة فعلية |
| حظر المستخدم | `PATCH /api/v1/admin/users/:id/status` | تحقق خادمي، إلغاء الجلسات وإخراج المستخدم من المقاعد |
| طرد المستخدم | `POST /api/v1/admin/users/:id/kick` | إلغاء الجلسات الحالية فقط؛ لا يمنع تسجيل الدخول لاحقًا |
| الغرف | `GET /api/v1/admin/rooms` و`PATCH /api/v1/admin/rooms/:id/status` | عرض وفتح/إغلاق |
| إشراف الغرفة | `GET/POST /api/v1/admin/rooms/:id/moderation` | تعيين مشرف الغرفة، كتم، طرد 60 ثانية، حظر دائم ورفع الحظر؛ الصلاحية من Worker |
| مشرفو التطبيق | `GET /api/v1/admin/moderators` و`PATCH /api/v1/admin/users/:id/role` | تعيين/إزالة دور admin أو moderator؛ المالك فقط |
| المحافظ | `GET /api/v1/admin/wallets` | عرض الرصيد وسجل الحركات الفعلي؛ المالك والمدير |
| إضافة عملات يدوية | `POST /api/v1/admin/users/:id/wallet/credit` | المالك فقط، مع سجل معاملة وتدقيق؛ ليست بوابة شحن |
| إعدادات أرباح الهدايا | `GET/PATCH /api/v1/admin/gifts/settings` | قراءة للمالك والمدير؛ تغيير النسب للمالك فقط |
| كتالوج الهدايا | `GET/POST /api/v1/admin/gifts/catalog` و`PATCH/DELETE /api/v1/admin/gifts/catalog/:id` | إدارة الكتالوج للمالك فقط |
| طلبات الهدايا المخصصة | `GET /api/v1/admin/gifts/custom-requests` و`PATCH /api/v1/admin/gifts/custom-requests/:id` | مراجعة واعتماد/رفض للمالك فقط |
| سجل إرسال الهدايا | `GET /api/v1/admin/gifts/transactions` | جديد في فرع العمل؛ قراءة وبحث فقط للمالك والمدير |
| سجل التدقيق | `GET /api/v1/admin/audit` | يعرض الإجراءات المسجلة في D1 |
| Agora | `GET /api/v1/admin/agora/status` و`PATCH /api/v1/admin/agora/voice` | قراءة وتحكم خادمي بالصوت |
| حسابات مديري اللوحة | `GET/POST /api/v1/admin/accounts`، و`PATCH /api/v1/admin/accounts/:id/role`، و`PATCH /api/v1/admin/accounts/:id/status`، و`POST /api/v1/admin/accounts/:id/password` أو `revoke-sessions` | جديد في فرع العمل؛ المالك فقط |

### سجل التدقيق

- الإجراءات الحساسة تكتب إلى `admin_audit_logs` مع هوية المدير.
- migration `0031_admin_audit_actor_refs.sql` تضيف جدول ربط مستقلًا بين سجل التدقيق وحساب المدير، مع `ON DELETE RESTRICT` على حساب المدير حتى لا تُحذف هوية المنفذ من السجل.
- واجهات إنشاء المدير وتغيير دوره وتعطيله وتدوير كلمة مروره وإبطال جلساته تكتب سجل التدقيق داخل نفس D1 batch.
- أُضيفت خطوة تطبيق migration `0031` إلى Workflow النشر اليدوي للـ Worker. لم تُطبّق migration على D1 الإنتاج حتى الآن.

## حالة المحفظة والهدايا وVIP والشحن

فحص D1 الإنتاجي للقراءة فقط بتاريخ 2026-11-12 أكد وجود `user_wallets` و`wallet_transactions` و`gift_catalog` و`gift_transactions` و`gift_custom_requests` ودفاتر أرباح الهدايا. في لحظة الفحص كان الكتالوج يحتوي 4 هدايا نشطة، وسجل الهدايا 8 معاملات ناجحة، وطلبات الهدايا المخصصة صفرًا، وعدد المحافظ 3. هذه أرقام لقطة وقت الفحص وليست بيانات ثابتة.

- **الهدايا:** الكتالوج، نسب الأرباح، طلبات الهدايا المخصصة، ومعاملات الإرسال لها مخطط وخدمات فعلية. سجل المعاملات الجديد للوحة قراءة فقط ولا يعدل أو يعكس المعاملات.
- **المحفظة:** مرتبطة بسجل حركات فعلي. إضافة العملات يدويًا متاحة للمالك فقط وتسجل معاملة `admin_credit`؛ لا تُعرض كأنها عملية شحن مدفوعة.
- **السحب النقدي:** مغلق عمدًا؛ إعدادات السحب والربط بالوكالات غير مفعّلة ولا تُقبل طلبات سحب.
- **VIP:** لا توجد جداول أو عقود API تشغيلية لإدارة الاشتراك أو المستوى أو المدة.
- **الشحن الإلكتروني:** لا توجد جداول طلبات شحن أو مزود دفع أو Webhook موثق؛ لذلك يبقى غير مفعّل. لا تُنشأ عمليات أو أرصدة شكلية.
- **Laravel:** لا توجد عقود مالية أو إدارية فعالة فيه؛ كل الربط الحالي عبر Worker.

## ما لم يكتمل

1. اعتماد نموذج VIP حقيقي: المنتج، المدة، الصلاحيات، التجديد والانتهاء وسجل المعاملات.
2. اعتماد مزود دفع وشروط التحقق من Webhook ومطابقة المبالغ قبل إضافة الشحن الإلكتروني.
3. اعتماد إجراءات السحب والوكالات والتحقق المالي قبل فتح السحب.
4. إضافة سبب ومدة انتهاء منظّمة لحظر الحساب/الغرفة؛ حظر الغرفة الحالي دائم والطرد المؤقت دقيقة واحدة، والسبب ليس حقلًا مستقلًا في سجل الحظر.
5. توفير مسار استرداد آمن لكلمة مرور المالك؛ لا يوجد حاليًا API لإعادة ضبطها، ولا ينبغي تنفيذ تعديل مباشر غير موثق على الإنتاج.
6. اختبار تكامل فعلي لإدارة حسابات المديرين بعد تطبيق migration `0031` على بيئة D1 معزولة، ثم نشر Worker بعد نجاح جميع الفحوص.
