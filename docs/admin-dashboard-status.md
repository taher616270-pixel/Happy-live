# حالة لوحة إدارة Happy Live

آخر مراجعة: 2026-11-08

## البنية الفعلية

- الواجهة مستقلة عن Flutter: `frontend/web/admin/index.html` وتُقدَّم من Pages على المسار `/admin/`.
- واجهة المستخدمين الأساسية تبقى في تطبيق Flutter؛ لا يوجد اعتماد على مسار Flutter لعرض لوحة الإدارة.
- الخادم النشط هو Cloudflare Worker في `backend/worker/src/index.ts`، وقاعدة البيانات D1 هي `happy-live-db`.
- Laravel في `backend/` هيكل تاريخي غير نشط. ملف `backend/routes/api.php` يحتوي حاليًا على فحص صحة فقط، و`backend/README.md` يحدد Worker بوصفه الواجهة الخلفية المعتمدة. لذلك يجب عدم إضافة وظائف الإدارة إلى Laravel أو افتراض أن لديه عقودًا تشغيلية.

## المصادقة والصلاحيات الحالية

- حسابات الإدارة وجلساتها منفصلة في `admin_accounts` و`admin_account_roles` و`admin_sessions`، ولا تعتمد على جلسة مستخدم عادي.
- تسجيل الدخول: `POST /api/v1/admin/auth/login`. تُخزَّن تجزئة رمز الجلسة في D1، ومدة جلسة الإدارة 12 ساعة.
- كلمات المرور تستخدم PBKDF2-SHA256 مع salt، بحد أدنى 100,000 دورة.
- حد محاولات تسجيل الدخول المشترك مع المصادقة هو 8 محاولات لكل عنوان IP خلال 15 دقيقة.
- التهيئة الأولى: `GET /api/v1/admin/auth/setup-status` و`POST /api/v1/admin/auth/setup`. تتطلب التهيئة سر Worker باسم `ADMIN_SETUP_TOKEN` وكلمة مرور من 12 حرفًا على الأقل، وتُسمح مرة واحدة.
- حالة قاعدة الإنتاج عند المراجعة: اكتملت تهيئة المالك، ويوجد حساب إداري نشط واحد باسم `owner`. لا تُخزَّن كلمة المرور في المستودع ولا يمكن استرجاعها من التجزئة. لا توجد حاليًا نقطة API لإعادة تعيين كلمة مرور المدير؛ لا تخمّن كلمة مرور ولا تنفذ إعادة ضبط مباشرة على قاعدة الإنتاج.
- الخادم يستخرج دور المدير من سجل D1 المرتبط برمز الجلسة. لا يثق في حقل role يرسله المتصفح.
- الصلاحيات المعرفة في Worker:
  - `owner`: جميع الصلاحيات.
  - `admin`: قراءة لوحة المعلومات والمستخدمين والغرف وسجل التدقيق، وإدارة حالة المستخدمين وطرد الجلسات والغرف وقراءة/إدارة إعداد Agora.
  - `moderator`: قراءة لوحة المعلومات والمستخدمين والغرف وسجل التدقيق فقط.
  - إدارة أدوار مشرفي التطبيق محصورة بالمالك حاليًا.
- واجهات الجلسة: `GET /api/v1/admin/me` و`POST /api/v1/admin/auth/logout`.

## الوظائف المربوطة بعقود حقيقية

| القسم | نقاط API | الحالة |
|---|---|---|
| الرئيسية | `GET /api/v1/admin/overview` | مربوط بإحصاءات D1 الحقيقية |
| الإحصائيات | `GET /api/v1/admin/stats` | مربوط بأعداد المستخدمين والغرف والمنشورات والرسائل |
| المستخدمون | `GET /api/v1/admin/users` | بحث وقائمة حقيقية |
| حظر/رفع حظر المستخدم | `PATCH /api/v1/admin/users/:id/status` | يغيّر حالة الحساب إلى suspended/active، ويلغي الجلسات ويزيله من مقاعد الغرف عند التعليق |
| طرد المستخدم | `POST /api/v1/admin/users/:id/kick` | يلغي الجلسات الحالية فقط؛ لا يمنع تسجيل الدخول مجددًا |
| الغرف | `GET /api/v1/admin/rooms` و`PATCH /api/v1/admin/rooms/:id/status` | عرض الغرف وفتحها/إغلاقها |
| مشرفو التطبيق | `GET /api/v1/admin/moderators` و`PATCH /api/v1/admin/users/:id/role` | تعيين/إزالة دور admin أو moderator لمستخدم نشط؛ المالك فقط |
| سجل التدقيق | `GET /api/v1/admin/audit` | يعرض الإجراءات المسجلة في D1 |
| Agora | `GET /api/v1/admin/agora/status` و`PATCH /api/v1/admin/agora/voice` | حالة الخدمة والتحكم العام بالصوت من الخادم |

كل عمليات التعديل أعلاه تتحقق من جلسة الإدارة والصلاحية داخل Worker. لا تُجرى استعلامات D1 من المتصفح.

## الفجوات التي تمنع إكمال بقية الأقسام

1. **VIP والمحفظة والشحن والهدايا:** فحص مخطط D1 الإنتاجي أظهر عدم وجود جداول VIP أو أرصدة/محافظ أو معاملات شحن أو كتالوج هدايا أو سجلات إرسال هدايا. لا توجد نقاط API لهذه العمليات. يلزم أولًا اعتماد نموذج البيانات، مصادر الرصيد، سجل معاملات غير قابل للتلاعب، حالات طلبات الشحن، مزود الدفع/التحقق، وقواعد منح/انتهاء VIP. لا تُنشأ أرصدة أو عمليات شكلية ولا تعرض أرقامًا وهمية.
2. **إدارة الحظر والطرد داخل الغرف:** جداول `room_bans` و`room_kicks` و`room_moderators` موجودة، لكن لا توجد حاليًا عقود Admin API لعرضها أو تعديلها من لوحة الإدارة. يلزم تعريف صلاحيات المالك/المشرف، مدة الحظر، السبب، وفك الحظر وسجل التدقيق قبل إظهار أدواتها.
3. **إدارة حسابات مديري اللوحة:** توجد جداول الحسابات والأدوار والجلسات، لكن لا توجد واجهات API لإنشاء/تعطيل مدير أو تدوير كلمة مروره أو إبطال كل جلساته من المالك.
4. **ربط هوية المدير في سجل التدقيق:** الإجراءات الإدارية تحفظ حاليًا `adminId` و`adminUsername` داخل `details_json` مع `actor_user_id = NULL`. هذا يحفظ اسم المنفذ لكنه ليس ارتباطًا علائقيًا. التحسين الصحيح يحتاج migration يضيف `actor_admin_id` ومراجعة كل عمليات الإدراج والاستعلام قبل تطبيقه على الإنتاج.
5. **تفاصيل قرارات الحظر:** واجهة تعليق الحساب الحالية لا تسجل سببًا أو مدة انتهاء؛ يلزم عقد يحدد السبب، المدة، الجهة المنفذة، وإعادة التفعيل التلقائي قبل تحويلها إلى نظام عقوبات متكامل.

تبقى صفحة «خدمات المنصة» معطلة عمدًا وتوضح غياب عقود VIP والشحن والهدايا بدل عرض بيانات تجريبية.

## التحقق والنشر عند المراجعة

- GitHub `main` كان عند commit: `81302b70ffaa984980739a8a33cdc98dd02ef507`. آخر commits التي راجعتها بعد تغييرات لوحة الإدارة عدّلت Workflow بناء Android فقط.
- Cloudflare Pages: نشر الإنتاج للـ commit أعلاه اكتمل بنجاح، deployment `c9f70376-9e76-4dc0-984e-2b4d8a5f6e5b` بتاريخ 2026-11-08 06:21 UTC.
- Worker: آخر نشر ظاهر هو `c27bdc30-bfea-4ede-99e8-24484e83c9a7` بتاريخ 2026-11-08 04:15 UTC، ويوجه 100% من الحركة إلى version `87d2f750-41ab-4bd6-ae26-814af9ed2e84`.
- GitHub Combined Status لم يُرجع status checks لهذا الـ commit، وأداة جلب Workflow Runs المتاحة تقتصر على runs المرتبطة بطلبات الدمج؛ لذلك لم أؤكد نتيجة تشغيل Android APK على push.
- أُضيف `backend/worker/tests/admin-security-contract.test.mjs` وفيه 5 حواجز عقدية ثابتة تتحقق من مصدر دور المدير في D1، واشتراط الجلسة والصلاحية، وبيانات سجل التدقيق، وعدم اتصال الواجهة بـ D1 مباشرة، وعدم عرض خدمات مالية غير مدعومة كبيانات حقيقية.
- أُضيف `.github/workflows/worker-checks.yml` لتشغيل `npm run typecheck` و`npm test` عند تغييرات Worker وعلى طلبات الدمج.
- فحصت صياغة ملف الاختبارات بـ `node --check` وصياغة Workflow بـ Ruby YAML parser؛ كلاهما سليم. هذه فحوص صياغة فقط وليست تشغيلًا للاختبارات على ملفات المشروع.
- GitHub Combined Status لم يُرجع status checks حتى وقت التحديث، وأداة جلب Workflow Runs المتاحة تقتصر على runs المرتبطة بطلبات الدمج؛ لذلك لم أؤكد نتيجة CI الفعلية بعد. لا تُعد فحوص الصياغة بديلًا عن نجاح `npm run typecheck` و`npm test`.
- نجاح Pages build لا يثبت وحده نجاح فحوص TypeScript أو اختبارات Worker.

## الخطوات التالية الآمنة

1. إضافة اختبارات Worker للمصادقة، رفض الأدوار المزيفة، صلاحيات كل دور، وتسجيل التدقيق.
2. إضافة migration لربط `actor_admin_id` بسجل التدقيق، ثم نشرها بعد مراجعة نسخة D1 احتياطيًا.
3. تصميم عقود إدارة حظر الغرف ومشرفي الغرف على الجداول الموجودة.
4. اعتماد نموذج مالي موثق قبل إنشاء VIP والمحفظة والشحن والهدايا.
5. إضافة مسار آمن لتدوير كلمة مرور المدير وإدارة جلسات مديري اللوحة.
